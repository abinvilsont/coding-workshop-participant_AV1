Workflows

Supporting workflows

The flows around the lifecycle: getting signed in, escalating, assigning work, administering facilities and engineers, and telling people about changes.

EventWho is notified (never the person who did it)
Incident reportedAll admins
Engineer assigned or reassignedNew engineer, reporter and followers, previous engineer
Status change, priority change, details edited, public noteReporter, followers and assigned engineer; all admins while unassigned
Escalation or priority requestAll admins and assigned engineer
Internal noteAssigned engineer and all admins; never the employee
Escalation clearedReporter
Incident deletedReporter, followers and assigned engineer
Duplicate mergedDuplicate's reporter and followers (link to the main incident), main reporter, main engineer, duplicate's engineer

Who sees which notes

  • Employee: public notes on their own incidents and those they follow; cannot write internal notes.
  • Engineer: all notes on assigned incidents; can mark a note internal.
  • Admin: all notes on every incident.
  • No new notes once an incident is closed or cancelled. A comment added with a status change is saved as a note.

What each dashboard shows

  • Employee: waiting / in work / resolved counts and their own and followed incidents.
  • Engineer: new, in-progress and on-hold counts, capacity and availability, assigned tickets by priority.
  • Admin: unassigned, escalated, priority requests, awaiting closure; needs-attention list, engineer workload, facility counts, recent activity.

Repository

Where the code lives

Frontend

frontend/src/
  • App.jsx · router.js: hash routes #/, #/incidents, #/incidents/new, #/incidents/:id, #/admin/facilities, #/admin/engineers (admin only)
  • pages/: Login, Dashboard (engineer availability switch), IncidentList, NewIncident, IncidentDetail
  • pages/admin/: Facilities, Engineers, People (accounts and roles)
  • public/manifest.webmanifest · public/sw.js · public/icons/: installable app; the service worker caches app files, never /api/
  • components/: AppLayout (role-based nav; menu drawer on phones), NotificationBell, IncidentForm, IncidentTable (table, or cards on phones), Badges (status/priority chips, StatCard, Section), Reviews (stars), ThemeToggle (light ⇄ dark), Field (errors above the input) · hooks/useAction, hooks/useResponsive (React Responsive breakpoints: phone 699, tablet 959, wide tables 1099, admin top bar 1199)
  • theme.js: the Material UI theme with light and dark colour schemes as CSS variables (brand colours, chip colours for both schemes, type scale); index.html applies the saved scheme before React loads
  • services/: apiClient (token, quiet renewal under an hour left, 401 sign-out), authService, incidentService, adminService, notificationService

API service

backend/api-service/
  • function.py: Lambda entry (Mangum); a direct invocation {"action": ...} runs a database task instead
  • app/admin_tasks.py: status · init_db · migrate, using sql/ (a copy of backend/db, kept in sync by bin/sync-db-sql.sh)
  • app/api/routes/: auth, incidents, dashboard, facilities, engineers, users, notifications
  • app/api/deps.py: current user, role checks
  • app/services/permissions.py: all role rules
  • app/services/notifications.py: who is told about which change
  • app/models/ · app/schemas/: ORM and request/response shapes

Database and tooling

backend/db/ · bin/ · infra/
  • schema.sql: tables, enums, triggers, workload view
  • seed.sql: demo data, all passwords Password123!
  • migrations/: additive changes for existing databases (001: notifications)
  • bin/start-dev.sh: Postgres, LocalStack, deploy, proxy
  • infra/: Terraform finds each folder under backend/ and deploys it as a Lambda
